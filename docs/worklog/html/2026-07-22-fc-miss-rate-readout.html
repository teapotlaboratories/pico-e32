1. What the readout is

input_sched_stats(fed, miss, applied) on the scheduled backend already accumulated:

  • fed — valid fc-commands the board saw (incl. ring-drops that never made the table);
  • miss — commands that arrived after their target frame (a deadline miss) + ring-drops + table overflow — everything that failed to apply on time;
  • applied — commands that reached their active window.

miss/fed is the deadline miss-rate the whole fc-scheduled design turns on. This change makes it leave the board and get reported by the host drivers.

2. Firmware — the seam + the emit

  • Seam (input.h): declared input_sched_stats(...) (it was a definition with no declaration). Following the seam's own convention (each backend no-op's input_set_frame), the other four backends (stub / serial / touch / i2c) get a no-op stub that writes zeros, so main.cpp can call it for any compiled backend.
  • Emit (main.cpp): a periodic ASCII line TS <fed> <miss> <applied>, ~1×/s (every 60 Steps), gated to the scheduled backend and placed outside the step_us/draw_us timing window — so it perturbs neither the fps numbers nor any other build.
  • Distinct prefix TS (not T) so the host's telemetry parser skips it; and an ASCII line never contains 0xAA, so the binary telemetry reader's sync-scan skips it too — safe to interleave on either stream.

3. The applied-count bug — caught on the first board run

The first on-board run reported applied = 180 > fed = 111 — nonsensical. Root cause: input_poll runs more than once per frame-clock value (the fake-08 tick polls input ~2× per emitted fc on a 30 fps cart), and s_applied was ++'d at every fc==G poll — so a hold=1 command counted twice. fed/miss are counted once per ring-drain, so the miss-rate was already correct — only the redundant applied field doubled. Fixed with a per-command counted flag (tally once, at the first active frame; robust to poll frequency).

On-board applied for the room-(0,0) run — before vs after the fix

before · fc==G
applied = 180
after · counted flag
applied = 111 = fed

To scale (before = full track): the double-poll inflated applied to 180 ≈ 2× the 90 room commands; the counted flag brings it to 111, equal to fed (90 room + ~21 title-skip warmup). The host-test is unchanged (applied=7 — it polls once/frame, so old and new agree there).

4. Host — parse + report (cart-agnostic)

fc_sched.py (the single source of the wire protocol) gains parse_stats(line) → {fed, miss, applied, miss_rate} (or None), symmetric with encode_cmd. The three device drivers (fc_device.drive_device / drive_device_chain, live.drive_device_predictive) capture the latest TS line and print:

fc-scheduled miss-rate: 0/600 cmds missed the deadline (0.0%), 600 applied on time  [lead k=2]

The periodic readout lags the final tally by ≤1 s — immaterial when misses are ~0.

5. Verified — host, then hardware

  • Host protocol tests 9/9 (+2 new): parse_stats decodes TS (incl. a trailing \r and 0/0/0 without divide-by-zero) and rejects a T frame, an ESP log line, and malformed input — so it never misfires on the shared stream.
  • Input gcc host-test: input_scheduled.c still matches the Python twin (fed=8 miss=1 applied=7).
  • Full ESP32-S3 build exit 0.

On hardware (Makerfabs ESP32-S3, CP2104; board identified read-only via /dev/serial/by-id/ so the bench camera's tuning was untouched):

open-loop 100 M:            CLEAR at fc=464   · 0/111 (0.0%), 111 applied  [k=2]
100 M -> 200 M -> 300 M -> 400 M:  CLEAR at fc=1454  · 0/600 (0.0%), 600 applied  [k=2]
                                   fps over 723 game-frames: 7.6/28.5/30.0
0 deadline misses across a 600-command, 4-room, 723-frame run at k=2 — the design's core prediction, now measured on the board. applied == fed after the count fix; fc=1454 is bit-identical to the recorded 400 M clear (deterministic).

6. Open / next

Sweep the reported miss-rate vs lead k (1/2/3) and host low_latency on/off to confirm it moves as the sim's jitter model predicts — the quantitative half of IN-5's acceptance. At k=2 on this tuned path it reads a flat 0%; the interesting data is where it starts to climb (expect k=1 to show non-zero on a loose host). The number is now exposed on the board, so this is a straight experiment.

  • 2026-08-05 WiFi connectivity · S3 native + P4 via the ESP32-C6 A WiFi menu on both handhelds — one components/wifi STA front-end (scan / connect / status / NVS-persist / auto-reconnect) over two backends chosen by IDF target: native esp_wifi on the S3, esp_wifi_remote → esp-hosted → an on-board ESP32-C6 on the P4. The P4 took two fixes: esp-hosted's boot auto-init hangs before app_main (deferred to wifi_mgr_init, constructor neutralised at build time so the vendor tree stays pristine), and the SD + C6 fight over the single SDMMC host (moved the SD to SPI, freeing the SDMMC host for the C6).   • 2026-08-03 z8lua · soft-float int(fix32) → single srai Disassembling the built interpreter turned up a defect the "-O0→-O2" audit missed: the fixed-point VM was doing double-precision soft-float to extract an integer. Every int(fix32) — peek/poke addresses, shift/rotate counts, str[pos] — compiled to a three-call double round-trip (__floatsidf → __muldf3 → __fixdfsi) instead of one srai, because fix32's only non-explicit conversion is operator double() and a bare int(x) is ambiguous among its explicit integer casts (int ≠ int32_t). Fix = one line, an explicit operator int() in fix32.h (mirror of the committed fix32(int) constructor patch). Verified __fixdfsi gone from the hot functions on both archs; measured 2.48× (P4) / 2.23× (S3) on an int(fix32)-saturated micro-bench, output byte-identical. Upper bound for the op, not a whole-cart number (display 30 fps-capped). Uncommitted (weekday no-commit window); both boards reflashed known-good with it baked in.
  • 2026-08-03 SD cart launcher · native cover-art carousel (P4 + S3) Both handhelds now boot into a cart launcher. The P4's TF slot works over SDMMC once the card's rail is powered from the on-chip LDO (VO4) — the whole blocker (pins 43/44/39-42 were right; the timeout looked like a dead slot). A new native cover-art carousel (carousel_launcher.cpp) decodes each .p8.png label with lodepng, browses the SD folder tree (needed only the esp32 Host::listdirs() — the __cd/__listdirs chain was already in fake-08), and launches into the VM. Layout comes from a per-board seam board_carousel_layout(), so the same code runs on the S3 (320×480) and the P4 (480×800), both confirmed live. Dead end recorded: framebuffer-screenshot-over-serial stalls at a random 65–685 KB on the P4 USB-JTAG — the bench camera is the capture path. Playtested a racing cart end-to-end (carousel → launch → drive → game over) at ~30 fps — which surfaced + fixed an FPS-HUD bug (repainted only on value change, so the P4's full-width game overwrote it). Uncommitted; process gap (no prior TODO/as-you-go worklog) noted.

Made the host geometry-agnostic; touched shared z8lua (submodule) + fake08 host → re-verify S3 before landing.

  • 2026-07-28 ESP-IDF v5.4.2 → v6.0.2 migration Bumped the vendored ESP-IDF a major version so the S3 project shares a modern IDF with the incoming ESP32-P4 board — and proved it non-regressive first. The whole S3 migration was two small, backward-compatible changes: a driver-component-split REQUIRES fix (v6 broke the monolithic driver into esp_driver_*) and a board.cpp LEDC zero-init (v6 added struct fields + -Werror). The S3 board builds, boots (Picolibc — the old newlib boot-loop risk cleared), and runs — Celeste clears 100→300 M on hardware at fc=1016, 29.8 fps, camera-confirmed; the binary even shrank (969→899 KB, 5→12% free) on Picolibc. Every actively-used app builds (luabench, fake08, bench-cam); display-test/host are pre-v6 bit-rot (superseded). Total: 5 files, all valid on v5.4.2 too.
  • 2026-07-22 fc-scheduled deadline miss-rate readout Gets the on-device fc-scheduled deadline miss-rate off the board: input_sched_stats() existed in the firmware but was declared and called nowhere, so it's wired to a periodic TS <fed> <miss> <applied> telemetry line (distinct prefix, so the T parser and the binary sync-scan both skip it) that the host drivers parse and report as miss/fed per lead k. A first board run exposed an applied-counter double (input_poll fires ~2×/fc on a 30 fps cart) — fixed with a per-command counted flag. On hardware: 0/600 deadline misses (0.0%) at k=2 across the 100→400 M chain — the one number the sim can't give.
  • 2026-07-19 Play-test harness → a gym for agent-solved carts + FPS measurement Turned the one-off Celeste play-test into a reusable rig aimed at measuring real on-device FPS across full playthroughs of arbitrary carts, solved by an agentic AI (no human). Landed the restructure into test/playtest/ (M0), replay-from-root (M1), and the replay-able Trace contract with dual sim + device replay plus a host↔device frame-count sync (host +2/game-frame, anchored at plan_fc0) (M2); the beam search is demoted to an optional tool (M3). An eris savestate speed-up was investigated and PARKED as a multi-bug dead-end (u_proto heap-use-after-free + Vm::Step global-buffer-overflow, matching upstream 47c48ad). The pivot: the genericity lives in the environment — a deterministic gym a spawned solver agent drives — not in a fixed solver. On that gym: the agent's eyes (gym.py snapshot/filmstrip, M4), a spawned agent that solved Celeste hands-free and emitted a verified Trace (M5), on-device fps folded into the telemetry stream (achieved + headroom, M6), a cart-agnostic sim/device video pipeline (M7), and a one-call orchestrator (orchestrate.py) that folds both replays into a single report.json — all verified on the board (M8). Next: a non-platformer cart to prove genre-agnosticism (M9).
  • 2026-07-18 Driving Celeste through full levels, hands-free over serial The play-test now clears rooms 1 & 2 ("100 M" → "200 M" → "300 M") with no human on the controls. Each room's input is solved offline against a physics twin and delivered frame-synced to a new serial position-telemetry stream (TELEMETRY=1, INPUT_HOLD_FRAMES=1 — no cart/vendored edits, via Vm::ExecuteLua). Result: the same clears at frames 618 & 908, every run; camera confirms "200 M" and "300 M".
  • 2026-07-18 Celeste plays, but "fps is horrible" — the 60 Hz-resume fix First real cart end-to-end (Celeste through fake-08's own GameLoop), then "fps is horrible." Measured the work at ~6 ms/frame (162 fps capable), so it was pacing, not the S3. Two bugs: a 100 Hz FreeRTOS tick quantized the limiter (judder), and the host paced fake-08's 60 Hz-resume coroutine at 30 Hz — so 30 fps carts ran at half speed. Fixed with a 1 ms tick and setTargetFps(60); verified 60 Hz resume / correct 30 fps motion, serial-driven. Added an opt-in on-screen FPS HUD.

  • 2026-07-17 Chasing the room-transition spike (compute, not GC) Steady Celeste runs ~110 fps on the S3, but each room load costs a single ~95 ms frame. Heap-instrumented MEASURE_FPS shows those frames allocate ~54 KB (load_room spawning objects). Decisive test: made z8lua's GC lazy — the load-room spikes didn't budge, so it's inherent interpreter compute, not GC. No cheap fix; the lever is general z8lua speed, only if a hitch-free 60 fps is ever required.
  • 2026-07-17 fake-08 on-device fps: a 4.6× drawFrame fix Measured fake-08's real frame time on the S3 (Gate #2 had measured the VM with drawing stubbed). Found drawFrame at 16.5 ms — the 128 KB scaled framebuffer didn't fit internal SRAM and fell back to PSRAM. Fixed by blitting in strips from a 16 KB internal buffer (+ inlined nibble-unpack): 16.5 → 3.6 ms, ceiling 54 → 189 fps. The draw path is no longer the fps bottleneck — frame rate is now VM-bound on dense rooms.

  • 2026-07-16 Trying esp_lcd i80 instead of LovyanGFX: why colour “broke”, and a real comparison Built an esp_lcd i80 backend to settle whether it really renders “colour wrong” on the rev-1 pins. It's 1.5× faster (590 vs 393 fps, real zero-copy DMA) — but its colour is broken in a way byte-swapping doesn't fix: every bright fill renders the same teal, swap-invariant. A clean source theory (“just a byte swap”) that the hardware refuted. The old “colour wrong” comments were overclaims — esp_lcd had never been tested on the correct pins. Decision: stay on LovyanGFX.

  • 2026-07-16 The panel was never broken: this board is rev 1, and its LCD is on different pins Two days of “the panel is dead” resolved: this unit is Makerfabs' first revision, LCD on WR=35/DC=36/CS=37 — their newer N16R8 board moved it to 18/17/46 because octal PSRAM eats those pins. 288 fps, matching checksums and a clean init were all true and meaningless: the bus clocked into unconnected pins. Driver now LovyanGFX; Gate #1's fps is void.

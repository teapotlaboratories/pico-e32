Feasibility — MIPI-DSI on this board (IDF v6.0.2)

  • esp_lcd/dsi ships the DSI bus + DBI (command) + DPI (video) driver.
  • P4 DPHY LL present (esp_hal_lcd/esp32p4/.../mipi_dsi_phy_ll.h); SOC_MIPI_DSI_SUPPORTED 1.
  • No chip-revision guard in the DSI path — the driver does not refuse early silicon.
  • DPHY power = internal LDO channel 3 @ 2500 mV (P4-fixed; from the IDF DSI test board).
  • No built-in ST7701 in IDF — use the managed esp_lcd_st7701 (takes a custom init) or hand-roll DBI.

Implementation + first light (VERIFIED — satisfies GP-4)

No esp_lcd_st7701 component is vendored, so the driver is hand-rolled in board.cpp against IDF's built-in esp_lcd/dsi (self-contained, no download). board_lcd_init: LDO ch3 power → reset G5 → esp_lcd_new_dsi_bus (2×500) → esp_lcd_new_panel_io_dbi + 37-cmd ST7701 init via tx_param + DCS 0x11/0x29 → esp_lcd_new_panel_dpi (34 MHz, RGB565, PSRAM FB) → backlight G23. Fill flushes the FB with esp_cache_msync; rgb565 is standard LE (no swap).

Serial — board_lcd_init -> ESP_OK; ST7701S/MIPI-DSI up: 480x800, 2-lane @ 500 Mbps, DPI 34 MHz. Every stage (LDO, bus, all 37 DBI writes, sleep-out/display-on, DPI init) returned ESP_OK — so the DPHY works on early v1.x silicon, the one thing feasibility couldn't settle on paper.
Camera (the oracle) — the P4 panel (right of the two-panel frame; S3 Celeste idle is centre) lit on the first flash. RGB fills initially blew out orange — the camera was tuned dark for the S3, so the panel was just bright, not miscoloured. Dropping the relay's exposure resolved the four corner markers: RED-TL · GREEN-TR · BLUE-BL · WHITE-BR, exactly as drawn. Therefore: colour order correct (no BGR swap), orientation upright (rotation quirk not needed), and the ESPHome-sourced config is validated on this exact board. Evidence: /tmp/pico-e32-captures/gp3-markers.jpg.

GP-5a · Serial input backend ported to P4 — VERIFIED

To unblock input without physical access, ported the S3's input_serial backend. Only the transport is board-specific (S3 = UART0; P4 console = native USB-Serial-JTAG), so input_serial.c is now conditional on CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG — one file, S3 path byte-for-byte unchanged. pico-e32-p4-hello drives an on-panel marker: l/r/u/d move it, z=O green, x=X red.

Verified end to end over serial — injecting keys on /dev/ttyACM0 and reading the log back on the same USB-JTAG link: rrr → held=0x02, x 220→320; ddd → 0x08, y 380→480; z → 0x10; x → 0x20; lll → 0x01, x 300→200. Masks match input.h exactly and the marker tracks — host → USB-JTAG → backend → app all work. Camera-confirmed: the cyan marker renders on the P4 panel and moved between two frames (top-left → lower). Also fixed a pre-existing latent v6 -Werror=misleading-indentation in input_serial.c (the S3's v6 builds used the scheduled backend, so this file hadn't been recompiled on v6).

GP-7 · Feature parity — real Celeste on the P4 (RISC-V) ✅ core

Built the existing pico-e32-fake08 app for the P4 board — same runtime, same cart, same board.h seam: DEFS='-D CELESTE=1 -D FORCE_FLASH_CART=1 -D CENTER_GAME=1 -D INPUT_BACKEND=serial'. Three S3-neutral changes: (1) host geometry-agnostic — ESP32Host.cpp computes OX/OY at runtime from the panel size the app passes to Host(BOARD_LCD_H_RES,V_RES) (S3 320×480 unchanged; P4 auto-centres 256² → 112,272 on 480×800); (2) fake08 app REQUIRES += esp_lcd esp_mm; (3) the RISC-V z8lua fix below.

★ RISC-V z8lua bug (the real blocker) — first P4 boot panicked bad conversion number->int → boot-loop. Instrumented the check: ti=-4660 (ok) but tu=0 — lua_tounsigned(fix32(-0x1234)) gave 0, not 0xFFFFEDCC. llimits.h's generic lua_number2unsigned runs through a floor()/modulo path in double, then casts a negative double to unsigned — which wraps on Xtensa but RISC-V saturates to 0 (fcvt.wu). Fixed in z8lua's fix32 config: convert via int32 ((LUA_UNSIGNED)(int32_t)(n)), never double — arch-independent. This is the "RISC-V re-validation" risk made concrete.
Camera-verified — real Celeste renders on the P4 panel: the title screen (gp7-celeste-title.jpg) and, after serial input drove it in, a gameplay room (gp7-celeste-play.jpg). Serial: loading celeste.p8 → entering GameLoop → serial input on USB-Serial-JTAG, no panic. z8lua + fake-08 + display + input all work on RISC-V — feature parity with the S3.
Gate #2 re-validated on RISC-V — a MEASURE_FPS build driven into gameplay: Step ~5–6 ms + drawFrame ~2.7 ms ≈ 8 ms/frame → ~120 fps of headroom (worst-frame ~13–21 ms at room transitions; one-time 121 ms cart-load spike). That's ~2× the S3 (Xtensa 240 MHz, ~15.8 ms/frame), so Celeste is comfortably 30/60-fps-capable, capped to the 30 fps target by the pacer. Draw is cheap — the DSI blit is fast. Heap-free ~32 MB. Gameplay video captured (gp7-celeste-p4.mp4).
Shared-file caveats — GP-7 touched components/z8lua/luaconf.h (a submodule; needs a gitlink bump to land) and ESP32Host.cpp — both shared with the S3. The z8lua fix is a strict correctness improvement and the host change is 320/480-identical on S3, but neither was re-run on the S3 this session. Re-verify S3 Celeste before landing.

SD cart launcher · native cover-art carousel

2026-08-03 · boot into a browser of the microSD's PICO-8 library and launch a cart by selecting it — built on the P4, then made panel-agnostic and confirmed on the S3

Both handhelds now boot into a cart launcher. The P4's TF slot works over SDMMC once the card's rail is powered from the on-chip LDO (VO4) — the whole blocker; the pins were right all along. A new native cover-art carousel (carousel_launcher.cpp) decodes each .p8.png label with lodepng, browses the SD folder tree, and launches into the VM. Layout comes from a per-board seam (board_carousel_layout()), so the same code runs on the S3 (320×480) and the P4 (480×800). One dead end recorded: framebuffer-screenshot-over-serial is unreliable on the P4 USB-JTAG — the bench camera is the capture path.

1. P4 SDMMC — the on-chip LDO was the blocker

The TF slot is on the P4 SDMMC slot-0 IO_MUX pins (4-bit), but the first mount failed identically every time — send_op_cond (1) returned 0x107 (ESP_ERR_TIMEOUT), the ACMD41 command-line handshake never answered. That signature reads as wrong pins / dead slot; it wasn't.

E sdmmc_common: sdmmc_init_ocr: send_op_cond (1) returned 0x107
E vfs_fat_sdmmc: sdmmc_card_init failed (0x107)
W board.p4: SD mount failed (ESP_ERR_TIMEOUT)          # before the LDO fix
...
I board.p4: SD mounted at /sdcard (29820MB, 4-bit, CLK43 CMD44 D0-3=39/40/41/42, LDO VO4)   # after

Diagnosis → fix — the failure looked like pins, but it was power

Ruled out pins and bus width; the card's 3.3 V rail is fed by the on-chip LDO, which esp-idf doesn't bring up for you (Arduino's SD_MMC does).

Takeaway for all P4 SDMMC here: the SD rail is powered by on-chip LDO VO4 (sd_pwr_ctrl_new_on_chip_ldo, ldo_chan_id = 4) — bring it up as host.pwr_ctrl_handle before esp_vfs_fat_sdmmc_mount. Pins + channel are in the P4 board doc.

2. Folder navigation — one Host method

Carts live in genre folders, so the launcher walks subdirectories. That machinery was already in fake-08: the browser calls __listdirs()→Vm::GetDirList()→Host::listdirs(), and __cd()→Vm::ChangeDirectory() (handles .., absolute, relative). The only gap was the esp32 Host::listdirs(), a return {} stub — filled by porting the gcw0 version (opendir-probe each entry, since FatFs doesn't set dirent.d_type). Recorded in the port code map.

3. The native cover-art carousel

A .p8.png is a 160×205 PNG whose visible pixels are the cart's label art. The launcher (firmware/pico-e32-fake08/main/carousel_launcher.cpp, new) decodes it with lodepng — the same decoder fake-08's Cart loader uses — and renders a centred cover thumbnail, breadcrumb, a position bar, and two neighbour "peek" slices, all confined to the game's on-screen column. It polls the shared input_poll() seam (touch when shipped, serial for headless tests) and, on select, hands the chosen cart's path to the VM. Repaint is split (full only on a directory change; in-place on an item move) to avoid flicker.

Deliberate divergence (flagged): this is a native launcher, not fake-08's built-in DefaultCart Lua browser — but it lives in the app, not the components/fake08 runtime, so the 1-to-1 port is untouched. Native buys full panel resolution + colour and board-driven layout.

4. Dead end — framebuffer screenshot over serial

Tried the existing FB_DUMP path for crisp camera-free captures. It does not work reliably on the P4 USB-Serial-JTAG and is recorded so nobody re-runs it:

  • A raw 768 KB blob hard-stops at a random point — 65 KB, 170 KB, 632 KB, 685 KB across attempts. Chunking made it worse (consistent ~685 KB). Same family as the known P4 "USB-JTAG drops long reads" note.
  • Compressing to get under the stall floor hit a miniz tdefl wall: MINIZ_NO_ZLIB_APIS removes mz_compress2; the one-call helper MZ_MALLOCs a ~300 KB compressor in internal RAM (exhausted → returns 0). Fixed by putting the tdefl_compressor in PSRAM + the callback streaming path (with TDEFL_COMPUTE_ADLER32) — a flat carousel screen then crushes to ~8 KB and transfers cleanly, but the game still tears and the whole thing is fragile.
  • Conclusion: the bench camera is the capture path (the primary HIL evidence anyway). FB_DUMP stays as a dev-only aid, off by default.

5. Board-relative layout → S3 port

The layout was hardcoded to the P4 panel (a 384-wide game column) — on the S3's 320-wide panel that gives a negative offset. Moved it into a per-board seam board_carousel_layout() (declared in each board.h, implemented in each board.cpp); the carousel reads it once.

6. Playtest — carts launch and play, at 30 fps

End-to-end on the P4, driven headlessly over serial (a temporary INPUT_BACKEND=serial build), camera-recorded: carousel → [Racing] → launch the first cart ("Don't Fear the Wormhole", a space racer) → accelerate + steer registered (accrued distance) → ran to "GAME OVER — NEW HIGH SCORE! 3.00.18 LI'YRS". A first attempt hit [RPG] not [Racing] (off-by-one: [RPG] sorts before [Racing] — uppercase P < lowercase a) — a free confirmation that a different cart type launches too.

On-screen FPS — and a HUD bug it surfaced. With -D SHOW_FPS=1 the generic meter (ESP32Host::waitForTargetFps) repainted the HUD only on value change, assuming it "lives outside the game blit region." True on the S3, not the P4: the game fills the panel width (384 @ x48) and blits over the HUD spot (panel (8,8)) every frame — so at steady fps it was drawn once, overwritten, invisible. Fixed to repaint every tick (tiny box, negligible cost); the racing cart then reads ~30 fps in play (36 on the menu). Small fake08 submodule change, off by default.

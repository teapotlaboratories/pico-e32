WiFi off by default · on-demand only

2026-08-06 · WC-5 — stop the radio being a permanent resident: acquire it, use it, tear it all the way down

The radio no longer comes up at boot on either board. A refcounted wifi_mgr_acquire() / wifi_mgr_release() brings it up only for whoever needs it, and the last release tears the stack completely down — esp_wifi_deinit, netif destroyed, and on the P4 esp_hosted_deinit() so the ESP32-C6 stops being linked at all. Launching a cart forces it down regardless. Memory returned when idle: 126.5 KB (P4), 38.0 KB (S3), with no leak across repeated cycles.
Honest null result: this did not improve loading time. Cover-art load is 64.0 ms median with the radio off — identical to with it on. The idle radio was not stealing throughput from the SD path. Of the three goals, only battery and CPU-residency are actually served; see §5 for how far each is substantiated.

Lifetime of the radio

Nothing brings it up implicitly. Every arrow below is a deliberate acquire or release.

Boot sits entirely in the first OFF block: on the P4 the C6 is never reset and esp-hosted's priority-23 tasks never exist.

1. The model

wifi_mgr_acquire() brings the stack up and takes a reference; wifi_mgr_release() drops one and tears down at zero. Reference-counted so overlapping users compose — the WiFi screen and, later, an OTA check or a download can each hold one. wifi_mgr_shutdown() forces it down whatever the count.

Who acquires today: only Settings → WIFI, while that screen is open. It also runs wifi_mgr_autoconnect() on entry so the screen shows real state rather than a bare OFFLINE. The WC-4 features (NTP, OTA, downloads) are the future consumers. wifi_mgr_init() is gone from the public header — bring-up is internal and reached only through acquire.

2. What teardown actually releases

esp_wifi_disconnect(); esp_wifi_stop();
esp_event_handler_instance_unregister(...);   /* before deinit, so no event lands on a dead stack */
esp_wifi_deinit();
esp_netif_destroy_default_wifi(s_netif);
#if CONFIG_IDF_TARGET_ESP32P4
esp_hosted_deinit();                          /* drops the C6 link — the actual power win */
#endif

The long-lived primitives (mutex, event group, retry timer) are deliberately not destroyed: they are small, and keeping them removes a whole class of use-after-free race against a concurrent scan/connect. Everything guarding a one-shot allocation is reset so the next bring-up starts clean.

4. Two bugs found while testing

esp_hosted re-init looked broken and wasn't. The first cycle test showed acquire #2 producing no log at all — exactly what esp_hosted_init() hanging after a deinit would look like, which was the risk called out in the plan. Tracing the bring-up state machine (and each screen's entry) showed the bring-up was never reached: run_wifi was never called the second time. Worth the trace — the workaround for the imagined bug would have been to skip esp_hosted_deinit() and give up most of the power saving.

The actual bug: X backed out two screens. The serial input backend holds a tap for 6 frames (and a finger on the deck rests longer), so the X that closed the WiFi screen was still asserted when run_settings' loop polled next. Its prev was stale, so it read a fresh X edge and exited Settings too. Fixed by re-seeding prev = input_poll() after a submenu returns — the same pattern already used on screen entry — in both places it can happen. Pre-existing, but it lives in this flow.

5. Against the three goals

not met
Loading time. Measured, null result (§3). The radio wasn't in the way.
met
Battery — by construction, not measured. On the P4 the C6 is never brought up at boot and is unlinked when idle: a whole companion chip not running WiFi firmware. No bench power meter here, so the magnitude is unquantified — stated as structural, not measured.
partly
Cores for the game — structural, frame time not measured. esp-hosted's priority-23 tasks and the wifi driver task don't exist unless something acquired the radio, and a cart launch forces a teardown. The launcher-side null result suggests the idle radio's CPU cost was small, so the honest expectation is a small win. A gameplay frame-time comparison was not run.

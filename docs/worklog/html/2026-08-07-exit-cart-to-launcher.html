Exit a running cart back to the launcher

2026-08-07 · IN-6 — making the cart launcher a launcher

Once a cart launched there was no way back short of power-cycling: GameLoop() never returns and MENU pauses without offering anything. Holding MENU now restarts into the carousel — restart is the return path, at ~1.8 s with the SD mounted and the radio off. Mechanism verified end to end; the hold duration itself needs a finger on the deck.

The gap, and how it surfaced

Found by being asked a plain product question — "when in the game, how do I exit to the main menu?" — and not knowing the answer. Reading the code rather than guessing:

main.cpp:639   vm->GameLoop(); /* fake-08's own loop; never returns */
board.cpp:541  MENU -> INPUT_PAUSE -> Vm::togglePauseMenu()   flips a flag, pauses audio, renders nothing
vm.cpp:1247    //todo: pause menu here, but for now just load bios     <- upstream's intent, commented out

So MENU freezes and silences the cart; pressing it again resumes. There is no exit. A launcher holding 3145 carts plays exactly one per boot.

It was visible in my own tooling for days. Every screen-capture script took the in-game shot last, because the board had to be reset afterwards. The constraint was internalised as a workflow quirk and never written down as a defect.

Two implementations that cannot work

  • A watcher task. input_poll() is destructive on the serial backend — it drains the UART/USB-JTAG buffer and decrements hold counters — so a second caller would eat input the VM never sees.
  • Checking from the app. app_main is blocked inside GameLoop(), which never returns.

That leaves two per-frame paths: ESP32Host::scanInput() — architecturally the right home, but in the fake-08 submodule, so a separate repo PR plus a gitlink bump — and input_poll(), which is ours. The gesture went in the input layer, called from inside each backend's poll.

Restart is the return path. The launcher is ~1.8 s from reset with the SD already mounted and the radio off, so rebooting beats unwinding a loop documented never to return.

Two things the first attempt got wrong

  • Armed in the wrong place. main.cpp has five mutually-exclusive frame loops (MEASURE_FPS / TELEMETRY / FB_DUMP / GC_MANUAL / shipped) and the arm went inside one — so the gesture existed only in the shipped build, absent from exactly the dev builds where it gets exercised. Now armed once, above the ladder.
  • A poll count was the wrong unit. "72 polls ≈ 1.2 s at 60 Hz" silently changes length in any loop that is not 60 Hz — and four of the five are not. Now wall-clock.

Caught only because a sticky -D in the CMake cache meant the first hardware test ran the FB_DUMP loop rather than the shipped one.

Verified — and precisely how far

launch /sdcard/[Action-Adventure]/2-minute Picovania.p8.png
entering GameLoop (hold MENU to return to the launcher)
W input.exit: MENU held 30 ms — returning to the launcher (restart)
rst:0xc (SW_CPU_RESET)
carousel: carousel layout ...          <- back in the launcher
The 1.2 s duration is NOT verified, and cannot be over serial. The USB-Serial-JTAG transport batches input at roughly 1 Hz here — sending p every 40 ms, the backend saw 5 bytes, ~1 s apart. A held button is unrepresentable over that link, so the run above used a temporary 30 ms threshold and the real 1200 ms was restored after. Detect → restart → launcher is measured; the feel of the hold, and that a short tap still reaches PICO-8's pause, need a finger on the deck with the touch backend.

Review round — seven findings, all real

The review on PR #35 found seven, none of them style. Four changed the code.

The host test stopped linking. host_test/run.sh compiles test_input_scheduled.c as one translation unit against stub IDF headers; adding input_exit_check() broke it with undefined reference. It passes on main and failed on the branch — a test the repo ships and I never ran.
  • Armed where there is no launcher to return to. The carousel needs LAUNCHER and a mounted card, but arming was unconditional. On a card-less boot, holding MENU rebooted into the same cart from the top while logging "returning to the launcher" — session lost, nothing gained. Now gated on launcher_is_boot_dest.
  • A tap plus a stall could reboot the device. The threshold compared two polls that saw MENU held, with nothing required in between. One serial byte holds PAUSE for several polls, so a tap followed by carousel_fb_dump()'s multi-second transfer landed a "held" poll >1.2 s later and rebooted. Fixed with INPUT_EXIT_MAX_GAP_MS (250 ms).
  • INPUT_EXIT_HOLD_MS was unreachable. DEFS='-D X=Y' only sets a CMake cache variable, so the documented escape hatch (=0 to compile the gesture out) silently built the 1200 ms default with a live gesture. Now plumbed via target_compile_definitions.

The other three were comments and docs asserting untrue things: that nothing is lost on exit (cart save state is discarded — dset() only pokes RAM and every serialising path is bypassed by esp_restart()); that every backend calls the hook (the stub and the i2c skeleton did not — now they do, which matters because that file is the IN-3 skeleton for the physical-button handheld); and the input spec, which described the poll-counting design this work deliberately rejected.

ESP-IDF v5.4.2 → v6.0.2 migration

2026-07-28 · bump the vendored SDK a major version, keep the ESP32-S3 building / booting / running, and map the whole migration surface — motivated by the new ESP32-P4 board

Bumped the vendored ESP-IDF from v5.4.2 to v6.0.2 so the S3 project shares a modern IDF with the incoming Guition ESP32-P4 board (its MIPI-DSI stack needs it) — and proved the move is non-regressive first. The entire S3 migration was two small, backward-compatible changes (a driver-component-split REQUIRES fix + a LEDC zero-init). The S3 board builds, boots (Picolibc), and runs — Celeste clears 100→300 M on hardware, camera-confirmed. Every actively-used app builds on v6; the two that don't were already broken pre-v6 (superseded apps). Area doc / plan: docs/hardware/pico-e32-guition-jc4880p443c-p4.md; this log is the running record.

1. Why v6.0.2 + the one runtime risk

ESP-IDF v6.0 released 2026-03; v6.0.2 is the latest patch of the v6.0 line (v6.1 is beta/dev), supported to 2028. It is "mostly compatible with v5.x" but with real breaking changes. The one that matters for this board: v6 switches the default C library Newlib → Picolibc.

The Picolibc risk — the board's earlier boot-loop (board-recovery, 2026-07-20-celeste-closed-loop-fc-scheduled.md, commit 385a988) was a newlib recursive-stdio-lock configASSERT on the first printh. Picolibc could change that behaviour — fix it, or move it — so on-device boot was the thing verification had to check.

Reversible throughout: the submodule was pinned at v5.4.2 (f5c3654); revert is git -C vendor/esp-idf checkout f5c3654 && … submodule update, and the v5.4.2 toolchain stays in vendor/.espressif (installs are additive). Disk was never a constraint (785 G free).

2. The bump

  • git -C vendor/esp-idf fetch --depth 1 origin tag v6.0.2, checkout, submodule update --init --recursive.
  • make install → v6 toolchain into vendor/.espressif (IDF_TOOLS_PATH exported by the Makefile — never ~/). Later install.sh esp32 for the bench-cam target.
  • Both clean. git -C vendor/esp-idf describe --tags → v6.0.2.

3. S3 build — exactly two changes, both backward-compatible

A clean-configure S3 build (APP=pico-e32-fake08 BOARD=makerfabs-ili9488-r1) surfaced two v6 breakages, fixed in the tree:

(1) The driver-component split. v6 broke the monolithic driver component into per-peripheral esp_driver_*, and a component must now REQUIRES the specific one that provides its header — bare REQUIRES driver no longer re-exports them. IDF's own error said it: "input_scheduled.c includes driver/uart.h, provided by esp_driver_uart."

driver monolith → per-peripheral esp_driver_* (v6)

Each of our components/apps that reached into driver for a specific header now requires the split-out component instead. The legacy driver/i2c.h (bench-cam's camera SCCB) is the exception — v6 still ships it inside driver, so bench-cam keeps driver and adds the two split ones.

Fixed REQUIRES in 4 CMakeLists (components/input, components/sdcard_spi, firmware/pico-e32-fake08/main, firmware/pico-e32-bench-cam/main). The esp_driver_* components exist since v5.3, so every one of these is valid on v5.4.2 too — no fork, and a v5 revert still builds.

(2) LEDC struct init. boards/makerfabs-ili9488-r1/board.cpp's backlight_on() used partial designated initializers for ledc_timer_config_t / ledc_channel_config_t. v6 added fields (deconfigure, intr_type, sleep_mode, flags) and promotes -Wmissing-field-initializers to a hard error. Fixed by zero-initializing (= {}) then assigning — clean on both v5.4.2 and v6.0.2, and future-field-proof. (These were warnings on v5; v6 made them errors.)

4. On-device verification — the real Picolibc test

Flashed the v6 build (board identified read-only via /dev/serial/by-id/*CP2104* → so no esptool probe disturbed the bench camera's tuning), then drove Celeste over the fc-scheduled path:

python3 test/playtest/celeste/fc_device.py /dev/ttyUSB1 --openloop --to300
  -> CLEAR at fc=1016 ; fps 9.9/29.8/30.0 ; PASS  (100 M -> 200 M -> 300 M)
  • Boots clean — no boot-loop. The Picolibc risk is cleared; the first-printh newlib-assert path is gone and the board comes up normally.
  • Celeste runs and clears at fc=1016 (bit-identical to the v5 result — deterministic), fps 29.8 avg (matches v5). Telemetry, the fc-scheduled input backend, and per-frame draw timing all work.
  • Display camera-confirmed (bench cam http://192.168.7.135, de-distorted + uprighted): the panel renders the room correctly, backlight on, colours right, green "30 FPS" HUD — which covers the LEDC/backlight change. A still + a video of the 100→300 M clear (throwaway /tmp).
Verified end to end — build + wire-level (boot / game logic / input / fps / draw timing) + camera-on-glass (display). The Newlib→Picolibc switch is the notable win: the board boots fine and the binary got smaller (§6).
Compile-only on v6 (honest gap) — the run used FORCE_FLASH_CART + INPUT_BACKEND=scheduled, so the SD-card mount path and the touch backend (esp_driver_i2c / i2c_master on v6) compile but were not run on hardware here. Low-risk (standard IDF APIs, driver-split verified at build time), but not exercised.

6. The whole surface + the size win

Total v6 migration = 5 files, all backward-compatible: the vendor/esp-idf submodule bump, the driver-split REQUIRES in 4 CMakeLists, and the board.cpp LEDC zero-init.

fake-08 app binary — v5.4.2 vs v6.0.2 (bar ∝ size; app partition = 1 MB)

v5.4.2 · newlib
969 KB · 5% free
v6.0.2 · picolibc

To scale (v5's 0xf2470 ≈ 969 KB = full track): the v6 build (0xe0a60 ≈ 899 KB) is ~7% smaller, taking partition headroom from 5% → 12% free. The Newlib→Picolibc switch is the cause — a smaller C library, for free.

State + landing plan

  • Board: the S3 CP2104 board holds the v6 Celeste build, idle after the clear — a known-good state.
  • Tree: uncommitted at time of writing. Code change → feature branch idf-v6-migration + PR + /review before a rebase-merge; the submodule gitlink bump is part of it. This worklog + this HTML render land in the same change.
  • Decision: keep v6. Follow-ups: the superseded display-test/host apps (retire or trivially revive), and then the ESP32-P4 board (GP-1…GP-4) — now on a modern IDF with proper MIPI-DSI support, which is what motivated the bump.

Killing the soft-float int(fix32) in the z8lua hot path

2026-08-03 · "is there an assembly-level optimization left in z8lua?" → disassemble the built interpreter, act on what it shows

The fixed-point VM was doing double-precision soft-float to extract an integer. Every int(fix32) — peek/poke addresses, shift counts, string indexing — compiled to a three-call double round-trip (__floatsidf → __muldf3 → __fixdfsi) instead of a single srai, because fix32's only non-explicit conversion is operator double() and a bare int(x) is ambiguous among its explicit integer casts. A one-line operator int() fixes it everywhere. Measured 2.48× (P4) / 2.23× (S3) on an int(fix32)-saturated micro-benchmark, output byte-identical.

1. How it was found

Disassembled the built interpreter object on both targets (…/z8lua/CMakeFiles/__idf_z8lua.dir/lvm.c.obj), attributing every libgcc soft-float / soft-divide call to its enclosing function and source line (objdump -drl + addr2line -i, vendored toolchains). The hot dispatch loop carried a cluster of double-precision calls that has no business in a fixed-point VM:

function__muldf3__floatsidf__fixdfsi__divdi3
luaV_execute9873
luaV_gettable111—
luaV_peek111—

Every one of those __fixdfsi / __floatsidf sites mapped to fix32.h:34 — operator double() — arranged as a fix32 → double → int round-trip, i.e. int( double(fix32) ). It fires wherever the VM extracts an integer from a number:

  • integer-keyed table access t[i] — luaH_get/arrayindex (ltable.c:131,488) convert the fix32 key via lua_number2int → (int)(n). The hottest one, and it lives in ltable.c, not lvm.c — found only in the second pass (see §6).
  • luaV_peek (lvm.c:251, int(a) & 0xffff) — every peek/poke and the @/%/$ operators
  • OP_SHL/SHR/LSHR/ROTL/ROTR (luaconf.h:582-586, the int((b)) shift/rotate count)
  • luaV_gettable (lvm.c:140, the PICO-8 str[pos] string-index shortcut)

Ordinary arithmetic (+ - * < >, band/bor/bxor) is already pure integer and was untouched. The residual double in OP_POW (fix32::pow = fix32(std::pow(double,double))) is legitimate — transcendental and cold. The 3 __divdi3 are the known fix32 divide, previously measured as low-value under the 30 fps display cap. Both left alone.

2. Root cause — an ambiguous cast falling back to double

fix32 has eight explicit integer conversion operators (int8_t…uint64_t) but no operator int(), and int is a distinct type from all of them — int32_t is long on both ESP toolchains. So int(x) matches none exactly, overload resolution finds the int8_t/int16_t promotions equally ranked (ambiguous), and silently falls back to the only non-explicit conversion: operator double().

What int(fix32) resolves to

No exact int match → the explicit integer operators tie → the lone implicit path wins, and it's the expensive one.

This is the exact mirror of a committed 2026-07-14 local patch — a fix32(int) constructor for the int → fix32 direction, whose comment already notes "int32_t is 'long', leaving plain 'int' uncovered so int→fix32 is ambiguous." Same disease, other direction.

3. The fix

One line in components/z8lua/fix32.h, alongside the other cast operators, gives int(x) an exact match:

inline explicit operator int() const { return m_bits >> 16; }
before — int(fix32)
call  __floatsidf
lui   a5,%hi(.LC0)
lw    a2,%lo(.LC0)(a5)
lw    a3,%lo(.LC0+4)(a5)
call  __muldf3
call  __fixdfsi
# + stack frame (sp, ra)
after — int(fix32)
srai  a0,a0,16
ret

Verified at the compiler level (isolated .cpp, -O2 -march=rv32imafc) and in the rebuilt interpreter objects: __fixdfsi is gone from luaV_execute/peek/gettable on both P4 and S3; the only double left is OP_POW's std::pow.

Correctness. m_bits >> 16 is arithmetic-shift floor; the old double path truncated toward zero. They differ only for negative fractional inputs — which never occur for shift counts, peek addresses, or string indices (all non-negative integers). The benchmark's result is byte-identical before/after on each board, confirming no behavioral change on the exercised paths.

The reproducible state is the idle title/attract (mode-7 running, dead-stable step); active racing swings 5.5–40 ms by scene and is too noisy to A/B cleanly.

~2.5% off the interpreter step — the expected "small" outcome: the racer is mode-7 mul/div + draw-bound, so int(fix32) (peek/shift) is only a minor share (≈4% of Step). And at the title the cart is compute-bound at ~116 fps vs the 30 fps display cap (≈4× headroom), so this is CPU-time / power headroom, not observable fps — exactly the caveat below. Build-system gotcha found here

The make wrapper passes DEFS as CMake cache variables, so a -D from one build persists into the next until fullclean. An earlier -D LUABENCH had stuck, silently running the halt-bench in place of later builds (including the "shipping" reflashes). Fix: make fullclean before a build whose define set shrinks. Both boards were rebuilt clean afterward.

Gun-FPS playtest — the cart class that benefits most (P4)

A raycaster FPS is the ideal real-world test: CPU-heavy and peek/t[i]-heavy (map + texture sampling) — exactly the fix's hot paths, unlike the racer's mul/div mode-7.

  • POOM (Doom demake) — boots but hangs at level-load ("ENTERING HANGAR", steady ~16 ms). POOM's reload()-based level decompression is a known emulator pain point; not playable on fake-08 as-is. (Also the genuinely heavy one — ~37 ms/frame during load.)
  • Wolfenstein 3D — plays: title → 🅾️ starts it → the 3D raycasted maze renders with the gun HUD (SCORE/HEALTH/AMMO), driven over serial, confirmed on the bench camera. Moving ≈ 14 ms step + 3 ms draw ≈ 59 fps compute-bound (smooth at the 30 fps cap).

Not observable as fps here (Wolf3D has headroom at the 30 fps cap), but a heavier raycaster (POOM's ~37 ms/frame) would cross into observable territory — the strongest evidence the fix is worth more than the racer alone suggested.

5. Scope & honesty

This bench is deliberately int(fix32)-saturated, so 2.2–2.5× is the upper bound for that operation, not a whole-cart number. Real-cart gain is proportional to a cart's peek/poke and bit-shift density and — because the display is 30 fps-capped — is only observable as fps when a cart is CPU-bound. A memory-tricks / blitter cart hammering peek will feel it; the racer and Celeste won't.

Still worth landing: a one-line, strictly-better-codegen fix for a genuine "soft-float in a fixed-point VM" defect, lower CPU load/power across the board, and de-risked for any future CPU-bound cart. The divide hand-roll remains not-worth-it.

6. Second adversarial pass — no new lever

Swept every libgcc soft-float/soft-div/soft-mod call across all z8lua objects (not just lvm.c) on the fixed P4 build, attributing each to a function and source line:

  • Hot machinery is clean: ltable, lstring, ldo, lgc, lfunc have zero soft-float/div/mod sites.
  • ltable being clean is the headline — the fix already de-soft-floated lua_number2int, i.e. integer-keyed table indexing t[i], the hottest op in gameplay carts. (The earlier table bench used string keys t.a — the hash path — so it never exercised this.)
  • Remaining soft-float is cold or assessed: OP_POW (std::pow, rare); luaO_arith (arithmetic fallback, not the inlined fast path); luaV_tostring/luaO_str2d (number↔string, needs double for %f); and the fix32 divide (low-value under the 30 fps cap).
  • fix32 primitives optimal: * → mul/mulh, % → hardware rem.

Conclusion: no further worthwhile assembly-level lever in the interpreter. The one real hot-path soft-float defect was int(fix32), now fixed, and its reach includes the hottest op.

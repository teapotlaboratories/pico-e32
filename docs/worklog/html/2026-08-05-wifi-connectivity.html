WiFi connectivity · S3 native + P4 via the ESP32-C6

2026-08-05 · a WiFi menu on both handhelds — one front-end, two radio backends — and the P4/C6 coexistence puzzle (WiFi + display + SD in one boot)

A single components/wifi STA front-end (scan / connect / status / persist / auto-reconnect) drives two backends chosen by IDF target: native esp_wifi on the S3, esp_wifi_remote → esp-hosted → an on-board ESP32-C6 on the P4. The launcher's WIFI menu (scan + on-screen keyboard) is identical on both. S3: verified end-to-end. P4: verified after solving two traps — esp-hosted's boot auto-init hangs before app_main (deferred + neutralised at build time), and the SD + C6 fight over the single SDMMC host (moved the SD to SPI). Net: one P4 boot now mounts the SD and links the C6 and renders the launcher.

One front-end, two radio backends — and the P4's resource split

The launcher menu and wifi_manager are shared; only the backend + the P4's host wiring differ.

blue = S3 path · amber = P4 path. The two boxes above the dashed frame are the radio stack; the dashed frame is why SD + WiFi can coexist.

1. One API, two backends

components/wifi/wifi_manager.{h,c} is a thin esp_wifi STA manager: a mutex serialises boot-autoconnect vs. the menu, an event group turns the async connect into a blocking wifi_mgr_connect(ssid, pass, timeout), and persistence is ours in NVS (WIFI_STORAGE_RAM so esp_wifi doesn't double-store). It's written to the plain esp_wifi.h API — which is exactly why the P4 reuses it: esp_wifi_remote re-implements that same API and forwards the RPCs to the C6. Per-target code is tiny:

  • CMake — S3: esp_wifi esp_netif esp_event nvs_flash; P4 adds esp_wifi_remote esp_hosted. esp_wifi_remote re-implements the API but does not re-export the header, so esp_wifi must stay in REQUIRES for esp_wifi.h to resolve — a build error that looked like a missing dep but is by design.
  • A short #if CONFIG_IDF_TARGET_ESP32P4 block in wifi_mgr_init brings the C6 up first (§3).

An earlier no-op wifi_manager_stub.c for radio-less targets is gone — the P4 has a real backend now.

2. The WIFI menu + on-screen keyboard

Settings → WIFI (gated on BOARD_HAS_WIFI) shows status/IP, scans the air into a selectable list, and on select opens a deck-driven on-screen keyboard (d-pad to move, O to type, MENU to submit) for the password, then connects and persists. Board-driven layout keeps it correct on both panels. Follow-up (WC-2): the PICO-8 font is uppercase-only, so a lowercase password displays uppercase — it is stored with correct case, so joins work; lowercase glyphs are a small font-table add.

3. Trap #1 — esp-hosted's boot auto-init hangs before app_main

esp-hosted inits itself from a C global constructor (__attribute__((constructor)) → ESP_ERROR_CHECK(esp_hosted_init())), before app_main. In a minimal probe that's fine; in the full firmware it stalls the P4 in the C6 SDIO bring-up — the boot log reaches H_SDIO_DRV: sdio_data_to_rx_buf_task started and dies, app_main never runs.

Fix — defer to app_main. wifi_mgr_init (P4 branch) does the bring-up explicitly, after board init:

esp_err_t he = esp_hosted_init();              /* starts the transport tasks */
if (he != ESP_OK && he != ESP_ERR_INVALID_STATE) return he;
he = esp_hosted_connect_to_slave();            /* blocking: reset C6 (GPIO54), SDIO init, identify slave */
if (he != ESP_OK) return he;

Neutralising the constructor cleanly. esp-hosted has no Kconfig to disable the auto-init, and its managed_components/ copy is git-ignored (regenerated from the lockfile) — hand-editing it is neither tracked nor durable. So the project CMake transforms that one call at configure time: the component manager fetches esp-hosted byte-identical to upstream, an idempotent string(REPLACE …) comments out the constructor's esp_hosted_init(), and it re-applies after any clean/re-fetch. Matches the repo's "keep the vendor tree byte-identical, push integration into the build" rule.

4. Trap #2 — SD and C6 share one SDMMC host

The P4 has a single SDMMC host. The microSD is on slot 0 and the C6's SDIO link on slot 1 — but one host can't be inited twice, so whichever comes up first locks the other out.

OrderResult
SD first (old SDMMC path)C6 handshake fails — host already claimed
C6 firstSD mount → ESP_ERR_NOT_FOUND
SD over SPI (fix)both work — SDMMC host is entirely free for the C6

Fix — drive the SD over SPI. The same TF pins run in SPI mode (CLK→SCLK, CMD→MOSI, DAT0→MISO, DAT3→CS), reusing the S3's existing BOARD_HAS_SD + sdcard_spi seam, so main.cpp needs no P4-specific SD path. board_sd_config() fills the SPI wiring and still powers the card rail (on-chip LDO VO4 — required in SPI mode too). Pins: SCLK 43, MOSI 44, MISO 39, CS 42. BOARD_HAS_SDMMC and the P4's board_sd_mount() were removed.

5. Result — coexistence, one boot

board.p4: SD over SPI2: SCLK43 MOSI44 MISO39 CS42, rail on LDO VO4
sdcard_spi: SD mounted at /sdcard                 <- SD works over SPI
carousel: carousel layout: game 48+384, ...       <- launcher up
H_API: ESP-Hosted starting ...                     <- from app_main, not the constructor
transport: Identified slave [esp32c6]              <- C6 radio linked
wifi: STA up                                        <- esp_wifi STA running

The ordering confirms the deferred path — esp-hosted starts after the SD mount and carousel, i.e. from the launcher's wifi_mgr_init. Launcher framebuffer verified via FB_DUMP (P4 compressed SHTZ). Driver-level connect was proven earlier with a standalone probe (joined Tukang Ketoprak, IP 192.168.7.212); nothing on the radio side changed since. S3 verified end-to-end (IP 192.168.7.228).

6. Review pass — measurements & fixes

Code review surfaced six issues; all are fixed on the branch, and one turned out to be a measurement rather than a change.

SD throughput after the move to SPI (measured)

Instrumented cover_rgba() temporarily to time the read+decode of a .p8.png cover, scrolling the carousel to force uncached loads:

SPI clockcover load (n=9)result
20 MHz (shipped)min 49.4 · median 64.0 · mean 65.9 · max 82.6 msworks
40 MHz—card init fails — send_csd returned 0x108, mount returns ESP_ERR_INVALID_RESPONSE

So 20 MHz is the practical ceiling on this wiring — the TF pins run through the GPIO matrix with no external pull-ups and the card won't negotiate 40 MHz. Two things follow: the bandwidth lost relative to SDMMC 4-bit can't be bought back by raising the clock, and it doesn't much matter — SDMMC cannot coexist with the C6 at all, so the real choice was "SD over SPI" vs "no WiFi". 64 ms to reveal a not-yet-cached cover is fine for a browse UI, and covers are cached after first view. A failed mount also degrades gracefully (continuing without SD) rather than panicking.

Behavioural fixes

  • P4 boot no longer waits on the radio. wifi_mgr_init() ran inline on the launcher thread and blocks ~2.3 s in the esp-hosted handshake, delaying the menu on every boot for a feature most sessions never touch. Moved to the existing background task — measured deck drawn at 1775 ms, down from 4068 ms, with the C6 still finishing at ~4.0 s, just off the critical path.
  • WiFi no longer dies permanently after 3 drops. One retry counter served both the modal connect and the steady-state link and only reset on GOT_IP, so an AP reboot left the handheld offline until a manual reconnect. Now two policies: bounded retries while wifi_mgr_connect() waits (the menu still gets a definite answer), and an indefinite slow retry (10 s) once a link has actually been established. An explicit disconnect/forget stands the keepalive down.
  • wifi_mgr_init() is now thread-safe, not merely idempotent. Making boot-init async meant the background task and Settings → WIFI could both pass the s_inited check and run the bring-up twice. Guarded with a statically-initialised spinlock; the loser waits for the winner.
  • 32-byte SSIDs now work. strlcpy into the 32-byte, not-NUL-terminated wifi_config_t.sta.ssid silently dropped the last character, so such networks just failed to join. Now memcpy with an explicit length; the passphrase is capped at its protocol maximum of 63 and WIFI_PASS_MAXLEN corrected from 64 to 63.
  • Init failure is reported — the return value was discarded at both call sites; the menu now says RADIO UNAVAILABLE instead of a generic offline state.
  • Partial-init retry no longer leaks — a failure after netif creation left s_inited false, so a retry would create a second netif and re-register handlers.

7. Commands run · board state

All builds go through the top-level make wrapper (never raw idf.py — the board overlay owns CONFIG_IDF_TARGET, PSRAM and flash size):

# P4 — dev build used for the coexistence test (serial input + framebuffer screenshots)
make flash APP=pico-e32-fake08 BOARD=guition-jc4880p443c PORT=/dev/ttyACM0 \
     DEFS="-D LAUNCHER=1 -D FB_DUMP=1 -D INPUT_BACKEND=serial"

# P4 — shipping touch build (what the board is left on)
make flash APP=pico-e32-fake08 BOARD=guition-jc4880p443c PORT=/dev/ttyACM0 DEFS="-D LAUNCHER=1"

# S3 — WiFi foundation build
make flash APP=pico-e32-fake08 BOARD=makerfabs-ili9488-r1 PORT=/dev/ttyUSB0 DEFS="-D LAUNCHER=1"

The configure step prints -- esp-hosted: deferred boot auto-init out of the C constructor (P4 C6 SDIO). when the build-time transform applies — its absence on a P4 build means the patch didn't take. Boot evidence was captured by pulsing RTS (reset) and reading the console for ~20 s; the P4 screenshot came from the FB_DUMP build's PAUSE-triggered compressed dump (SHTZ → zlib → 480×800 RGB565).

That's the stronger evidence here — the exact scan-out pixels, no camera framing/glare/mirror ambiguity — and it now works on both boards. The camera adds nothing this change depends on (no new display code); physical output was confirmed by eye.

P4 SD back on SDMMC · host handed to the radio on demand

2026-08-06 · WC-6 step 1 — recover the throughput the SPI move cost, now that the radio is on-demand

The P4's single SDMMC host is now handed back and forth: the SD owns it while browsing and playing, and gives it up for the duration of a WiFi session. Who owns the SDMMC host

One host, two claimants. Ownership moves; it is never shared.

Step 2 (WC-6) adds a third state — SD on SPI while the C6 holds the host — for downloads that need both at once.

1. Why the SD can have the host back

The P4 has one SDMMC host: slot 0 is the TF card, slot 1 is the on-board C6. They cannot be initialised at the same time, which is why the SD went to SPI — with an always-on radio there was no other option. Since the radio became on-demand it is off for the overwhelming majority of the time, so nothing wants slot 1.

The open question was whether the host can be handed over rather than claimed once. It can — the original finding was only about simultaneous init:

Read is 7.1× faster; decode is unchanged and is now ~75% of what remains. Further gains have to come from the decoder — the bus is no longer the bottleneck.

3. The trap: do not deinit the host yourself

The first unmount added an explicit sdmmc_host_deinit() after the VFS unmount. That panics the board into a boot loop — Guru Meditation Error, MCAUSE 0x1f, immediately after the unmount log. Cause: esp_vfs_fat_sdcard_unmount() already releases the host and frees the card (IDF vfs_fat_sdmmc.c, unmount_card_core()):

if (pdrv_num == 1) {
    call_host_deinit(&card->host);
    free(card);
}

So the explicit call is a double-deinit through freed state. Unmount, and nothing else — the comment on board_sd_unmount() says so, so it doesn't get re-added. Also deliberate: the LDO VO4 rail stays powered across the handover — it powers the card, is needed again on remount, and tearing it down costs ~300 ms of settling.

4. Shape of the change

  • board.{h,cpp} — back to BOARD_HAS_SDMMC + board_sd_mount(), plus a new board_sd_unmount() that releases the host. The SPI seam is gone from this board; step 2 restores it as the network-session mode.
  • main.cpp — the #elif BOARD_HAS_SDMMC mount branch is back.
  • carousel_launcher.cpp — run_wifi() unmounts before wifi_mgr_acquire() and remounts after wifi_mgr_release(), including on the acquire-failure path so a dead radio doesn't cost the card.

Sequencing lives in the app, not the wifi component. wifi_manager still knows nothing about storage and the board owns the driver; the launcher is the only place that knows both. Safe because nothing on the WiFi screen touches storage and the launcher holds no open file handles — cover art is decoded into PSRAM at browse time, not streamed. The S3 is untouched — native radio, no shared host, still SPI.
